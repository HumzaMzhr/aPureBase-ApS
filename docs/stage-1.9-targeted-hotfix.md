# Stage 1.9 — targeted first-voice and gap hotfix

1. **Exact root cause of the reported wrong first voice.** Not established for the user's microphone session: no recording or first-PCM trace from that session was available. The one approved controlled reproduction traced “Hej, godmorgen,” to the initial forced generation on the existing ElevenLabs WebSocket, configured with Isabella `gIfqD5jrnhkFu8ENVbXC` / `eleven_flash_v2_5`. It did not reproduce a provider/voice switch. The previous Stage 1.9 trace also labels the initial greeting as that voice. A different perceived timbre cannot be diagnosed as OpenAI/browser/system output from this evidence. No acoustic-quality pass is claimed.

2. **Exact voice fix.** Bind the gateway's public voice provenance to the same immutable configuration used to create its actual `ElevenLabsVoiceProvider` socket, instead of reading configuration again to label output. Give that socket a generation ID and tag each PCM delivery. Check the configured voice at the client READY message and subsequent frames; reject changed identity/generation metadata. The HCP renderer now requires an expected configured voice before its first sample, and LocalOutput validates provider/voice/model before changing alignment or admitting PCM. Metadata mismatches stop output and retain already-generated translated text; there is no replacement TTS. The 250ms prosody hold only submits text to the same socket; it has no second renderer/provider. First greeting force-flush, models, voice settings, pronunciation, precision, cached opening audio, pairing and normal UI were not changed. This strengthens and traces provider enforcement; it does not establish that a subjective greeting-timbre complaint is resolved.

3. **Evidence first and subsequent Danish audio use Isabella.** The one paid synthetic English→Danish run checked all 18 PCM packets and completed all nine semantic segments using exactly one identity: provider `ElevenLabs`, voice `gIfqD5jrnhkFu8ENVbXC`, model `eleven_flash_v2_5`, generation `0ff115b3-15f3-42bc-8203-d5885d79677a`. 4. **Exact reproduced gap cause.** The original microphone 7–11s interval cannot be reconstructed exactly without that session's trace. The saved Stage 1.9 introduction reproduces a roughly four-second wait: “mit navn er Humza,” was translated/submitted at source time 5.268s and received its first PCM at 9.584s. The already-translated short text was below the ElevenLabs generation threshold and waited for later text to fill the buffer. The configured 50/80/100/120-character schedule and initial greeting force-flush explain why the greeting played but the short following introduction stalled. The existing 250ms short-fragment hold accounts for only part of that 4.316s interval, not its full duration. ElevenLabs documents this threshold behavior and buffered-text flush ([official buffering documentation](https://elevenlabs.io/docs/eleven-api/guides/how-to/websockets/realtime-tts)). The new live trace additionally found translation readiness delays: introduction text became ready at 7.797s and 10.184s, while prior speech had already ended. Those upstream waits remain and were not optimized.

5. **Exact gap fix.** In the local simultaneous voice client, when submitted validated text remains unaligned and the real playback queue has at most 650ms remaining, request a buffered-text flush on the existing socket. Poll every 50ms, emit at most one request per newly-submitted text extent, and reject that command outside the simultaneous profile. This prepares N+1 as N drains and does not reconnect, replay, slow audio, crossfade, overlap speech, add audio silence or enlarge the jitter buffer. The provider schedule/settings stay unchanged. Ignore surplus protocol control whitespace in the original-text alignment ledger and the voice client’s outstanding-text counter so in-stream flushes cannot shift later semantic marks. Add memory-only segment/PCM provenance and GAP events with the requested positions, backlogs, buffer depth, last/next segment, phase changes and dominant observed wait. RMS diagnostics distinguish provider-generated quiet PCM from an empty renderer queue. Anchor diagnostic times to the audio clock, tolerate small clock jitter and close diagnostics on STOP. Pairing/output-routing code was unchanged; no broad latency optimization was performed.
